# โครงสร้างข้อมูล Firestore — ออเดอร์สั่งกาแฟที่โต๊ะ

> ส่วน B ของการบ้านที่ 1 (ADT-RAISE Module 2 สัปดาห์ที่ 6) · ขอบเขตดู `SCOPE.md` ที่ root ของ repo
> อ้างอิงความต้องการจาก [[../../01-requirements/01-spec/self-order|self-order]] · ร่างนี้ใช้เป็นต้นแบบให้ **ลอกลงกระดาษด้วยมือ**

## B1 — กติกา 4 ข้อ

1. 📁 **Collection** = โฟลเดอร์ · 📄 **Document** = ไฟล์ · ✏️ **Field** = ช่องข้อมูลในไฟล์
2. Firestore **ไม่มี JOIN**
3. จึงต้อง **จดชื่อซ้ำไว้ในไฟล์เลย** (denormalize) เช่นเก็บ `menuName` ไว้ในออเดอร์ตรง ๆ
4. ของที่เป็นของรายการนั้นโดยเฉพาะ ให้เป็น **โฟลเดอร์ย่อย** (subcollection) เช่นข้อความเรื่องออเดอร์นั้น

## B2 — โฟลเดอร์ 3 + โฟลเดอร์ย่อย 1

🔴 = ช่องที่จดชื่อซ้ำ ให้ **วงกลมสีแดง** บนกระดาษ แล้วเขียนข้าง ๆ ว่า "จดซ้ำเพราะไม่มี JOIN"

```
📁 users            → name · email · role
📁 menus            → name · price
📁 orders           → tableNo · customerId
                      menuId · menuName 🔴
                      size · sweetness · milk · quantity · totalPrice
                      note · status
                      baristaId · baristaName 🔴
                      createdAt
   └ 📁 messages    → authorId · authorName 🔴 · message · createdAt
```

| ช่องที่จดซ้ำ | จดจากไหน |
|---|---|
| 🔴 `orders.menuName` | `menus/{menuId}.name` |
| 🔴 `orders.baristaName` | `users/{baristaId}.name` |
| 🔴 `messages.authorName` | `users/{authorId}.name` |

**ค่าที่ใช้ได้**

- `users.role` → `barista` · `owner` · ผู้ใช้ในโฟลเดอร์นี้คือพนักงานร้านเท่านั้น ลูกค้าไม่มีบัญชี
- `orders.status` → `รับออเดอร์แล้ว` · `กำลังทำ` · `เสร็จแล้ว`
- `orders.size` → `เล็ก` · `กลาง` · `ใหญ่`
- `orders.sweetness` → `ไม่หวาน` · `หวานน้อย` · `หวานปกติ`
- `orders.milk` → `ไม่ใส่นม` · `นมวัว` · `นมโอ๊ต` · `นมอัลมอนด์`
- `orders.totalPrice` → ราคา ณ ตอนสั่ง จดไว้ในออเดอร์ ร้านขึ้นราคาภายหลังก็ไม่กระทบออเดอร์เก่า
- `orders.baristaId` · `baristaName` → ว่างไว้ `""` จนกว่าจะมีบาริสต้ารับทำ
- `createdAt` → ข้อความรูปแบบ `YYYY-MM-DD HH:mm` เรียงใหม่ไปเก่าได้ตรง
- ไม่มีช่องชื่อหรือเบอร์โทรลูกค้า ตาม PDPA ใน BL-08

## ข้อมูลตัวอย่าง (ชื่อสมมติทั้งหมด)

| id | ข้อมูล |
|---|---|
| `users/u001` | สมชาย ใจดี · barista |
| `users/u002` | สมหญิง รักงาน · barista |
| `users/u003` | สมศรี ตั้งใจ · owner |
| `menus/mn001` | อเมริกาโน่ · 50 บาท |
| `menus/mn002` | ลาเต้ · 60 บาท |
| `menus/mn003` | มัทฉะลาเต้ · 65 บาท |
| `orders/od001` – `od005` | 3 รับออเดอร์แล้ว · 1 กำลังทำ · 1 เสร็จแล้ว |
| `orders/od001/messages/ms001` | ข้อความของสมชาย |
| `orders/od002/messages/ms002` | ข้อความของสมหญิง |

## B3 — ตอบคำถาม 2 ข้อ

**① ถ้าบาริสต้าสมชายเปลี่ยนชื่อ ต้องไปแก้กี่ที่?**

ในข้อมูลตัวอย่างต้องแก้ **3 ที่**

- `users/u001` 1 ที่ ต้นทางของชื่อ
- `orders` ทุกใบที่ `baristaId = u001` 1 ที่ คือ od001
- `messages` ทุกรายการที่ `authorId = u001` 1 ที่ คือ od001/messages/ms001

ถ้าร้านเปลี่ยนชื่อเมนู "ลาเต้" ก็ต้องแก้ `menus/mn002` และออเดอร์ od001 · od004 อีก 2 ใบเช่นกัน
ยิ่งมีออเดอร์มาก ยิ่งต้องแก้หลายที่ แต่ชื่อเปลี่ยนน้อยมาก ส่วนหน้ารายการออเดอร์ถูกเปิดทั้งวัน การอ่านเร็วโดยไม่ต้อง JOIN จึงคุ้มกว่า

**② ทำไม `messages` จึงเป็นโฟลเดอร์ย่อย ไม่ใช่โฟลเดอร์แยก?**

- ข้อความแต่ละข้อความเป็นเรื่องของออเดอร์ใบนั้นโดยเฉพาะ แยกออกมาเดี่ยว ๆ ก็ไม่มีความหมาย
- หน้ารายละเอียดอ่านข้อความทีละออเดอร์เสมอ เปิด `orders/{id}/messages` ได้ตรง ๆ ไม่ต้องค้นทั้งฐาน
- เขียนกฎสิทธิ์ผูกกับออเดอร์แม่ได้ เช่น เฉพาะลูกค้าเจ้าของออเดอร์และพนักงานร้านเท่านั้นที่อ่านข้อความได้
- ข้อความเพิ่มได้ไม่จำกัด โดยไฟล์ออเดอร์ไม่ใหญ่ขึ้น
